# Littlebread Lab 구축 로드맵

## 문서 목적

이 문서는 Littlebread Lab을 브랜드 원칙에 맞는 기술 블로그로 구축하기 위한 실행 순서와 각 단계의 결정 범위, 산출물, 완료 조건을 정의한다.

구현 순서는 화면의 외형보다 콘텐츠와 읽기 경험을 먼저 안정시키는 것을 원칙으로 한다. 각 단계에서 아직 결정하지 않은 사항은 다음 단계의 표준으로 임의 확정하지 않는다.

## 전체 진행 순서

```text
1. 기술 기반 결정
→ 2. 콘텐츠 모델 설계
→ 3. 최소 정보 구조 확정
→ 4. 핵심 사용자 흐름 정의
→ 5. 디자인 토큰 구현
→ 6. Article 상세 화면 설계 및 구현
→ 7. 최소 기능 버전 구축과 실제 콘텐츠 검증
```

## 1. 기술 기반 결정

### 목표

콘텐츠 작성, 정적 생성, 품질 검사와 배포가 반복 가능한 개발 기반을 만든다.

### 확정 사항

- Next.js App Router와 TypeScript를 사용한다.
- GitHub Pages의 제약에 맞춰 `output: "export"` 기반의 정적 사이트로 운영한다.
- 콘텐츠 원본은 저장소 안의 Markdown 파일로 관리한다.
- 패키지 매니저는 pnpm을 사용하고 `pnpm-lock.yaml`을 커밋한다.
- GitHub Actions가 검사와 정적 빌드 및 Pages 배포를 담당한다.
- 분석 도구는 GA4를 최소 구성으로 사용한다.
- 스타일 기반은 CSS custom properties와 CSS Modules로 구성한다.
- 단위 검증은 Vitest를 사용한다. 브라우저 E2E 검증은 핵심 사용자 흐름이 생기는 단계에서 Playwright를 추가한다.

자세한 결정과 제약은 [`technical-foundation.md`](technical-foundation.md)를 따른다.

### 산출물

- 실행 가능한 Next.js 프로젝트
- 정적 내보내기 설정
- lint, typecheck, test, build 명령
- PR 검증 CI
- `main` 브랜치 GitHub Pages 배포 워크플로
- 환경 변수를 통한 GA4 연결점

### 완료 조건

- 로컬에서 모든 품질 명령이 성공한다.
- `out/`에 정적 HTML이 생성된다.
- 서버 전용 기능 없이 사이트가 동작한다.
- 배포 워크플로가 `out/`을 Pages artifact로 게시한다.

## 2. 콘텐츠 모델 설계

### 목표

글이 문제 해결 과정과 지식 간 연결을 일관되게 표현하도록 콘텐츠 구조를 정의한다.

### 주요 작업

- Article과 Project의 책임 구분
- Markdown 디렉터리 및 파일 이름 규칙 정의
- front matter 필수·선택 필드 설계
- Zod 기반 빌드 타임 검증
- 상태(`exploring`, `building`, `completed`) 의미 정의
- 카테고리와 topic의 역할 분리
- 선행 지식, 관련 글, 프로젝트, 다음 단계 연결 모델 설계
- 초안 글의 개발·배포 제외 정책 정의
- 수식, 코드, 표, 각주와 다이어그램 지원 범위 확정

### 주의할 점

- 모든 글에 하나의 본문 목차를 강제하지 않는다.
- `slug`, 읽는 시간처럼 계산 가능한 값은 가능하면 자동 생성한다.
- Rust 같은 도구를 최상위 브랜드 분류로 고정하지 않는다.
- 아직 정하지 않은 퀀트 프로젝트를 스키마의 전제로 만들지 않는다.

### 완료 조건

- 실제 글 예시가 스키마를 통과한다.
- 잘못된 메타데이터가 빌드를 실패시킨다.
- 글과 프로젝트 사이의 연결을 문자열 관례가 아닌 검증 가능한 형태로 표현할 수 있다.

## 3. 최소 정보 구조 확정

### 목표

실제 콘텐츠를 찾고 읽는 데 필요한 최소 경로를 정의한다.

### 현재 출발점

```text
Home
Articles
Projects
About
```

### 주요 작업

- 각 최상위 영역의 책임과 포함 콘텐츠 정의
- URL과 slug 정책 결정
- 카테고리를 URL, 메뉴 또는 필터 중 어디에 표현할지 결정
- 영구 링크 변경 정책 정의
- RSS, Sitemap, robots.txt와 404 경로 포함
- 콘텐츠가 적은 초기 상태의 빈 화면 처리 결정

### 완료 조건

- 모든 콘텐츠 유형에 하나의 대표 URL이 있다.
- 사용자가 Home에서 글까지 불필요한 우회 없이 이동할 수 있다.
- 분류 변경이 기존 글 URL을 불필요하게 깨뜨리지 않는다.

## 4. 핵심 사용자 흐름 정의

### 목표

Littlebread Lab의 Connection이 장식이 아니라 실제 탐색 경험으로 작동하게 한다.

### 핵심 흐름

```text
블로그 발견
→ 현재 다루는 문제 이해
→ 글 선택
→ 문제 해결 과정 읽기
→ 관련 지식 또는 프로젝트 탐색
```

### 주요 작업

- 사용자가 첫 화면에서 브랜드와 현재 관심사를 이해할 수 있는지 검증
- 글 목록의 선택 정보 정의
- Article 안에서 문제, 판단, 구현, 검증을 찾는 방법 정의
- 선행 지식, 관련 글, 프로젝트와 다음 단계의 연결 방식 정의
- 키보드와 모바일 환경에서 같은 흐름이 유지되는지 확인

### 완료 조건

- Knowledge Graph 없이도 관련 콘텐츠를 의미 있게 탐색할 수 있다.
- 모든 연결 요소가 실제 정보 관계를 표현한다.
- 사용성 검토 결과가 페이지 설계의 근거로 남는다.

## 5. 디자인 토큰 구현

### 목표

확정된 브랜드 팔레트와 타이포그래피 역할을 재사용 가능한 코드로 옮긴다.

### 주요 작업

- Background, Text, Border, Brand와 Accent 토큰 정의
- Pretendard 및 Geist Mono 폰트 제공 방식 결정
- 본문 크기, 행간, 제목 위계와 콘텐츠 폭 설계
- 간격, 선, 포커스와 상호작용 상태 정의
- 코드, 표, 인용문과 메타데이터의 기본 스타일 정의
- 성공·실패·금융 상승·하락을 브랜드색과 분리한 semantic color 설계
- 접근성 대비와 모션 감소 설정 검증

### 주의할 점

- 토큰을 만든다는 이유로 아직 미정인 카드나 레이아웃을 확정하지 않는다.
- Neutral 85%, Slate Blue 10%, Warm Brown 5%는 방향성이지 기계적인 화면별 할당량이 아니다.

### 완료 조건

- 기본 Markdown 요소만으로도 차분하고 정밀한 읽기 경험이 형성된다.
- 브랜드색과 타입페이스가 문서화된 역할 외에 남용되지 않는다.

## 6. Article 상세 화면 설계 및 구현

### 목표

블로그의 핵심인 문제 해결 기록을 가장 먼저 완성도 있게 읽을 수 있도록 한다.

### 주요 작업

- 제목, 설명과 메타데이터 위계 설계
- 게시일, 수정일, 읽는 시간과 상태 표현
- 본문, 코드, 표, 수식, 이미지와 출처 스타일 구현
- 긴 글의 탐색 방법과 목차 사용 여부 검증
- 문제 해결 단계의 표현 방식 설계
- 관련 지식, 연결된 프로젝트와 다음 단계 구현
- SEO metadata와 공유 정보 구현
- 모바일, 키보드, 스크린 리더와 긴 콘텐츠 테스트

### 완료 조건

- 실제 글을 데스크톱과 모바일에서 편안하게 읽을 수 있다.
- 메타데이터가 본문보다 시각적으로 우세하지 않다.
- 연결 정보가 장식이 아닌 다음 탐색 행동을 제공한다.

## 7. 최소 기능 버전 구축과 실제 콘텐츠 검증

### 목표

첫 공개에 필요한 최소 페이지를 연결하고 실제 콘텐츠로 전체 경험을 검증한다.

### 구현 순서

1. 공통 레이아웃과 내비게이션
2. Article 상세
3. Article 목록
4. Home
5. About
6. Projects 또는 초기 안내 상태
7. SEO, RSS, Sitemap과 404
8. GA4 운영 검증
9. 반응형, 접근성과 성능 검증

### 실제 콘텐츠 검증 항목

- 긴 제목과 긴 코드가 레이아웃을 깨뜨리지 않는가
- 표와 다이어그램을 모바일에서도 이해할 수 있는가
- 문제, 선택 이유, 구현과 검증 흐름이 드러나는가
- 메타데이터와 tag가 과도하지 않은가
- 관련 글과 다음 단계가 탐색에 도움이 되는가
- Warm Brown 강조가 Slate Blue와 경쟁하지 않는가
- 빈 목록과 진행 중인 프로젝트가 과장 없이 표현되는가

### 초기 공개 범위에서 보류 가능한 기능

- 검색
- 다크 모드
- 전체 Knowledge Graph
- 자동 OG Image 생성
- 복잡한 필터
- 댓글
- 게임화된 진행률

### 완료 조건

- 실제 글 2~3편으로 전체 흐름이 검증된다.
- 자동 검사와 Pages 배포가 안정적으로 반복된다.
- 미결정 사항과 후속 과제가 문서에 남아 있다.

## 단계 변경 원칙

- 다음 단계로 넘어가기 전에 현재 단계의 완료 조건을 확인한다.
- 실제 콘텐츠에서 드러난 문제는 이전 결정을 수정할 근거가 될 수 있다.
- 브랜드 가이드의 확정 사항을 바꾸는 결정은 구현 편의만으로 내리지 않는다.
- 새 의존성이나 외부 서비스는 해결하려는 문제, 대안과 운영 비용을 기록한 뒤 추가한다.
