# 블로그 리뉴얼 방향

작성일: 2026-11-05

## 범위와 순서

블로그를 전면 리뉴얼한다. 먼저 글 작성·콘텐츠 수집·빌드·배포 구조를 구축하고, 이후 디자인 시스템을 개편한다.

## 결정한 구조

| 역할 | 선택 |
| --- | --- |
| 글 작성 | Obsidian |
| 콘텐츠 백업·수집 원본 | Google Drive의 Markdown과 첨부 파일 |
| 사이트 프레임워크 | Next.js |
| 패키지 매니저 | pnpm (`package.json`의 `packageManager` 버전 기준) |
| 페이지 생성 | 정적 내보내기 (`output: "export"`) |
| 수집·검증·빌드·배포 자동화 | GitHub Actions |
| 호스팅 | GitHub Pages |

```text
Obsidian에서 작성
→ Google Drive에 백업·동기화
→ GitHub Actions에서 콘텐츠 수집·변환·검증
→ Next.js 정적 빌드
→ GitHub Pages 배포
```

글을 사이트 저장소에서 직접 작성하거나 커밋해서 발행하는 방식에서 전환한다. 저장소는 사이트 코드와 자동화 코드를 관리하고, 빌드에 필요한 글과 첨부 파일은 Google Drive에서 가져온다. Vercel은 이번 배포 대상에 포함하지 않는다.

React 컴포넌트의 브라우저 상호작용은 활용할 수 있다. 요청 시점 서버 처리에 의존하는 기능은 현재 정적 배포 범위에 포함하지 않는다.

## Obsidian 콘텐츠 관리

Obsidian 보관함이 있는 로컬 폴더와 Google Drive의 동기화는 사용자 환경에서 설정을 완료했다. 이후 설계 범위는 GitHub Actions 빌드에서 Drive 콘텐츠를 가져오는 인증·수집 방식이다.

Obsidian 보관함 루트를 기준으로 다음 폴더를 사용한다.

| 경로 | 역할 |
| --- | --- |
| `/assets` | 이미지와 기타 첨부 자료 |
| `/drafts` | 작성 중인 글 |
| `/posts` | 공개 대상 글 |
| `/templates` | 글 작성용 템플릿 파일 |

공개 대상 글은 `/posts`에서 관리한다. `/drafts`와 `/templates`의 문서는 공개 대상에 포함하지 않는다.

글의 메타데이터는 Obsidian 파일 속성(Properties)으로 관리한다.

| 속성명 | 타입 | 용도 | 공개 글 기준 |
| --- | --- | --- | --- |
| `title` | 텍스트 | 블로그에 표시할 글 제목 | 필수 |
| `created` | 날짜 | 글을 처음 작성한 날짜 | 필수 |
| `published` | 날짜 | 블로그에 공개한 날짜, 글 목록 정렬 기준 | 필수 |
| `updated` | 날짜 | 마지막으로 내용을 수정한 날짜 | 선택 |
| `description` | 텍스트 | 글 목록과 검색 결과에 사용할 짧은 요약 | 필수 |
| `slug` | 텍스트 | 파일명을 바꿔도 유지할 URL 식별자 | 필수 |
| `tags` | 태그 | 글의 주제 분류 | 선택 |
| `cover` | 텍스트 | 대표 이미지 경로 | 선택 |

`published`는 `/posts`로 옮길 때 직접 입력한다. 공개 여부는 폴더로 구분하므로 별도의 `draft`나 `status` 속성을 두지 않는다.

- 필수 속성이 누락되거나 비어 있으면 오류로 처리하며, 빌드에서 임의로 채우지 않는다.
- `created`는 글 생성 시 템플릿으로 입력하고 유지한다.
- `updated`는 의미 있는 내용 수정 시 직접 입력하며, 빌드 날짜로 덮어쓰지 않는다.
- 날짜는 `YYYY-MM-DD` 형식으로 작성하고, 날짜 판단은 한국 시간 기준으로 한다.
- 날짜 관계는 `created ≤ published`, `updated`가 있으면 `created ≤ updated`를 검증한다.
- `published`가 미래 날짜라는 이유로 오류를 내거나 발행을 보류하지 않는다. `/posts`에 있는 글은 날짜와 무관하게 공개 대상이다.
- `tags`가 없으면 태그 없이, `cover`가 없으면 대표 이미지 없이 표시한다.
- 글 목록은 `published` 내림차순으로 정렬하고 같은 날짜는 `slug` 오름차순으로 정렬한다.

## URL과 첨부 자료 규칙

- 글 URL은 `/posts/{slug}/` 형식으로 생성한다.
- `slug`는 영문 소문자·숫자·하이픈으로 작성한다. 예: `obsidian-blog-workflow`.
- 발행 후에는 제목이나 파일명을 바꿔도 `slug`를 유지한다.
- 첨부 자료는 Obsidian 보관함의 `/assets/{slug}/` 아래에 글별로 보관한다.
- 첨부 자료는 `/assets` 전체를 수집하되, 배포 대상은 공개 글의 본문과 `cover`에서 참조하는 자료로 한정한다.
- 공개 글 사이에 중복 `slug`가 있거나 참조한 첨부 파일이 누락되면 배포를 중단하고 오류를 안내한다.

메타데이터·URL 검증, 본문 변환과 참조 첨부 파일 선별·복사를 구현했다.

## Drive 콘텐츠 수집과 배포 범위

- 빌드마다 Drive의 `/posts`와 `/assets` 내용을 하위 폴더까지 전체 다운로드한다. `/drafts`와 `/templates`는 수집하지 않는다.
- 폴더 구조를 유지하여 빌드 작업 공간에 저장한 뒤, 로컬 파일을 기준으로 글 링크와 이미지 참조를 연결하고 검증·변환한다.
- 수집한 원본은 Git에 커밋하지 않는다.
- 배포 결과에는 공개 글과 해당 글의 본문·`cover`에서 참조하는 첨부 자료만 포함한다. 참조되지 않은 자료는 다운로드했더라도 배포하지 않는다.

```text
/posts와 /assets 전체 다운로드
→ 글·메타데이터 분석
→ 로컬 파일 기준 링크·이미지 연결
→ 검증·변환
→ Next.js 빌드·배포
```

전체 다운로드는 `scripts/fetch-drive.mjs`에 구현했다. `fetch-content.yml`은 main push·수동 실행에서 수집 → 검증·변환 → 공개 첨부 준비 → 정적 빌드 → Pages 배포를 연결한다. 실제 통합 배포 성공 여부는 병합 후 확인해야 한다. 설정과 수집 정책은 [Drive 수동 수집 설정](drive-content-setup.md)을 따른다.

## Drive 접근 인증

- GitHub Actions는 서비스 계정을 거치는 Workload Identity Federation(WIF)으로 인증한다.
- 빌드 전용 Google 서비스 계정을 만들고 Drive의 `/posts`와 `/assets` 폴더를 해당 계정에 읽기 권한으로 공유한다.
- WIF에서 허용한 이 저장소의 GitHub Actions 작업이 서비스 계정의 임시 인증을 받아 Drive API를 호출한다.
- 서비스 계정 JSON 비밀키를 발급·보관하는 방식은 사용하지 않는다.
- 서비스 계정 사용 권한과 Drive 폴더 읽기 권한은 각각 설정한다.
- 프로젝트 ID·서비스 계정 이메일·WIF provider·Drive 폴더 ID는 사용자가 GitHub Secrets에 직접 입력한다. 실제 값을 대화나 저장소 파일에 남기지 않는다.

Google Cloud 프로젝트·서비스 계정·WIF·Drive 공유·GitHub Secrets 설정과 실제 수집 검증을 완료했다. 인증은 main 브랜치의 `fetch-content.yml`만 허용하며, 배포 통합에서도 이 경로를 유지한다. 상세 절차는 [Drive 수동 수집 설정](drive-content-setup.md)을 따른다.

참고: [서비스 계정을 거치는 WIF 설정 문서](https://github.com/google-github-actions/auth#workload-identity-federation-through-a-service-account).

## Obsidian 문법 지원

| 항목 | 지원 방침 |
| --- | --- |
| 글 링크 | 다른 글로 연결하는 컴포넌트로 표시한다. 연결 대상 글이 `/posts`에 있는 경우에만 컴포넌트를 표시하며, 대상 글의 `/posts/{slug}/`로 연결한다. |
| 이미지 임베드 | `/assets` 안의 이미지를 참조하여 본문에 표시한다. 첨부 자료 수집·배포 및 누락 검증은 위 규칙을 따른다. |
| 콜아웃 | `note`, `tip`, `info`, `warning`, `danger`를 지원한다. 그 외 종류는 내용을 유지하고 기본 안내 상자로 표시한다. |

- 글 링크는 노트 파일 경로로 식별한다. 파일명만 작성했다면 `/posts` 안에서 유일하게 일치할 때 연결한다. 여러 노트가 일치하면 경로를 명시하도록 오류를 안내한다.
- 공개 대상 글이 없으면 링크 컴포넌트를 숨기고 표시 문구를 일반 텍스트로 유지한다. 이 경우는 배포 오류로 처리하지 않는다.
- 이미지는 `/assets` 기준 경로로 연결한다. 파일명만으로 여러 이미지가 일치하면 오류로 처리한다.
- 콜아웃 접기·펼치기와 노트 본문 임베드는 첫 버전에서 지원하지 않는다.

컴포넌트의 시각 디자인은 디자인 시스템 단계에서 정한다.

문법 변환과 글 목록·상세 화면 연결을 구현했다. 내부 링크는 공개 대상에만 연결되는 HTML 앵커로 표시하고 PostBody 컴포넌트에서 렌더링한다. 현재 스타일은 기능 확인용이며 리뉴얼 디자인 시스템의 확정을 의미하지 않는다.

## 발행 실행 방향

콘텐츠는 매일 아침 정기 실행으로 발행하고, 수동 실행도 지원한다. 정확한 실행 시각·시간대와 GitHub Actions 예약 실행 구성은 후속 단계에서 정한다. 콘텐츠 수집을 포함한 수동 발행과 main push 발행을 구현했다. 정기 발행은 아직 구현하지 않았다.

## 실패 처리와 배포 재현

- 일시적인 다운로드 오류는 제한된 횟수만 재시도하고, 계속 실패하면 배포를 중단한다.
- 콘텐츠 오류는 파일 경로·속성명·원인을 모아 안내한다.
- 수집·검증·빌드 단계에서 실패하면 기존 사이트를 유지한다.
- 수집 중 원본 변경을 감지하면 다시 수집하거나 해당 실행을 중단한다.
- 배포 기록에는 코드 커밋, 파일 목록·해시, 실행 시간을 남긴다.
- 실제 배포에 사용한 공개 글·첨부 자료와 빌드 결과를 30일 보관한다. 참조되지 않은 자료가 포함된 전체 `/assets` 수집본은 보관 대상에서 제외한다.

수집 단계에는 최대 3회 시도와 수집 전후 목록·버전 비교를 구현했다. 파일별 크기·MD5 확인과 SHA-256 manifest 생성도 포함한다. 공개 자료 선별 후 30일 보관과 복구 절차는 아직 구현하지 않았다.

## 패키지 관리

- 로컬 개발과 GitHub Actions 모두 pnpm을 사용한다.
- 일반 설치와 CI에서는 `pnpm install --frozen-lockfile`을 사용한다.
- 의존성 추가·수정은 `pnpm add`, `pnpm remove`, `pnpm update`로 수행하고 `package.json`과 `pnpm-lock.yaml`을 함께 커밋한다.
- npm·Yarn의 lockfile을 혼용하지 않는다.
- 개발은 `pnpm dev`, 품질 검사는 `pnpm check`, 정적 빌드는 `pnpm build`, 빌드 결과 미리보기는 `pnpm start`로 실행한다.
- Git 작업은 [Git 작업 규칙](git-conventions.md)을 따른다.

## 후속 설계 사항

- 통합한 Drive → Pages 발행의 병합 후 실제 배포 검증
- 매일 아침 정기 발행의 실행 시각·시간대와 GitHub Actions 구성
- 배포 콘텐츠·빌드 결과의 보관 위치와 복구 절차

## 현재 구현 상태

- Drive 전체 수집, 파일 무결성·수집 중 변경 검증, 메타데이터 검증, 본문 변환을 구현했다.
- 로컬 샘플 및 사용자 지정 콘텐츠로 동일한 준비·빌드 코드를 실행한다. 상세 절차는 [콘텐츠 발행](content-publishing.md)을 따른다.
- 홈 최근 글, `/posts/` 목록, `/posts/{slug}/` 상세, RSS·sitemap에 새 콘텐츠를 연결했다.
- 참조된 첨부만 `public/assets/`에 복사하고 이전 생성 첨부는 제거한다. 입력이 없는 배포 빌드는 실패한다.
- `fetch-content.yml`에 수집·빌드·배포를 통합하고 중복된 기존 deploy 워크플로를 제거했다. 병합 후 실제 발행 검증이 필요하다.
- 기존 소개·프로젝트·포트폴리오와 과거 `/articles/{slug}/` 페이지는 이번 범위에서 유지한다. `/articles/`는 새 글 목록 안내로 전환했다. 기존 디자인을 리뉴얼 기준으로 확정하지 않는다.
- 아침 정기 발행, 공개 콘텐츠·빌드 결과 30일 보관·복구, 디자인 시스템 개편은 후속 작업이다.

이 문서는 합의한 방향의 기록이며 구현 완료를 의미하지 않는다. 기존 문서의 저장소 내부 글 작성 방침은 이번 결정으로 대체한다. 그 외 기존 설계를 리뉴얼의 확정 사항으로 자동 승계하지 않으며, 브랜드·디자인 변경은 후속 단계에서 별도로 결정한다.
